## 二、故障 A：`介绍.标题` 死锁（你贴的日志，15:38 退出）

### 证据

- 四份候选校验报告**内容逐字相同**（三个修复策略各产一份，互不改进）：
  `自动恢复/f71bd64b…/validation_vpku4mkh|1p2xap3m|bs9hqi1t|lpf3ntv7/质量治理/周期审计/validate_delta_governance_*.txt`
  内容均为：`周期治理后介绍.标题必须为非空字符串；依据已处理原文生成完整简介，不得用占位文字或分析正文填充`
- 账本 `f71bd64b…/state.json`：`attempts = [targeted(worker_failed,65), evidence(worker_failed,65), diagnosed(diagnosis_failed,65)]`，`status=exhausted`
- 当时的校验实现（`git diff engine/scripts/governance_contract.py` 可见被删除的旧代码）：
  ```python
  for key in ("标题", "描述"):
      value = proposed.get(key, previous.get(key))
      if not isinstance(value, str) or not value.strip():
          errors.append(f"周期治理后介绍.{key}必须为非空字符串；…")
  ```

### 死锁链

1. 旧实现把 `标题` 与 `描述` **一并判硬 error**；
2. 本书 `介绍.标题` 长期为空（历史书名线索缺失）；
3. `周期审计.j2` 明令"标题有依据才补齐、不虚构" → 模型**永远不写标题**；
4. → 任何候选都必然判错 → 三个策略耗尽。**程序侧与模型侧要求互斥，无解。**

### 放大器（为什么烧掉 ~25 个 worker / 38 分钟）

- 修复任务包含 `audit_011-015.md`（286KB）+ `故事结构_增量.json`（501KB），超出输入容量；
- `bounded_generation.run_paged_recovery` 检测到超容量后，先走 `CapacityTree` 做**整包分片索引**；
- 日志实测：`worker context: 43 → 54 个只读任务材料`（**逐轮递增**），同一 hash 目录被重复调度 3 次（每个策略各来一遍）；
- 结果：≈25 个 `bounded_fragment` worker、38 分钟、零有效产出。

### 修复状态

16:04 已改：`governance_contract.py` 只拦"**显式破坏**已有标题"（非字符串 / 把已有非空标题改成空白），缺失或留空放行；`fault_recovery.py` 同时把 `governance_contract.py`、`governance_introduction.py` 加入恢复指纹，契约变更时旧账本自动归档重开。

**效果已验证**：`audit_011-015.status.json` → `committed_at 17:54`；其后 `audit_016-020.status.json` → `committed_at 20:22`。流水线已正常推进到第024章。

## 三、故障 B：第024章 Delta 修复空转（当前卡点）

### 证据

- `自动恢复/898d0fea…/state.json`：`task=repair_chapter`、`output=章节处理\Delta\第024章_第二十四章_一切待续.json`、`status=repairing`、targeted 已 `worker_failed`(rc=65)、evidence 于 20:45 启动
- `attempt_0001_01/contract.md` 的校验报告：10 条 error，**全部同型**
  `新增元素.事件[萧炎退回鉴宝室静候拍卖款项].详情[重量级] 值类型必须是 string 或 string[]，实际为int`（5 个事件 × 重复 2 次）
- **程序纠错零动作**：`attempt_0001_01/质量治理/delta校验/coerce_ch024.json` = `{"corrections": []}`
- 实际数据（`validation_fdr6cx2h/章节处理/Delta/第024章_第二十四章_一切待续.json`）：5 个事件把
  `涉及章节 / 发生地点 / 参与成员 / 重量级 / 分组 / 标签集` **整组写在 `详情` 里**，顶层只剩 `名称`、`时间`
- 目标文件 mtime 停在 20:39（模型未产出新候选），与"worker 空转"一致

### 链路

1. 模型把**事件集的标准顶层字段**整组塞进 `详情`；
2. `详情` 的值只允许 `string` / `string[]`，由 `story_schema_rules.py:336` 判**硬 error**（该行没有 mode 分支，process 阶段不降级）；
3. 其中只有 `重量级` 是 `int` → 唯一踩线字段（`发生地点/分组/标签集` 是 string、`参与成员` 是 string[]，所以不报错）；
4. **程序纠错修不了**：
   - `coerce_delta.relocate_element_fields:68` 是**单向**的（顶层 → 详情），不会反向搬运；
   - `coerce_delta.py:347` 的 `重量级` 分支只处理**顶层** `item["重量级"]`；
   - `normalize_story_schema.py` 只按 `DEFAULTS` 补顶层缺失值，**不清除** `详情` 内多余键；
5. → 该 error 没有任何程序侧消除路径 → 只能靠模型重写，而模型重写仍可能重复同样的组织方式 → 空转。

### 与故障 A 的结构同构

两者都是"**校验器在 process 阶段拒绝 + 程序侧无自动修复能力**"的组合。区别只在：A 是模型被提示词禁止满足（真死锁），B 是模型能修但程序侧无兜底、模型连续没做到。

## 四、三个结构性缺口（这才是"为什么又会出问题"）

| # | 缺口 | 具体位置 | 后果 |
|---|---|---|---|
| 1 | **校验不对称** | `story_schema_rules.validate_item_schema`：顶层缺标准字段在 process 降级为 warning（"normalize 将补齐默认值"）；但 `详情[key]` 类型错误在 336 行是**硬 error 且无 mode 分支** | 同一次"字段没放对"，一侧可自愈、一侧死锁 |
| 2 | **程序纠错单向** | `coerce_delta.relocate_element_fields:68` 只做「顶层→详情」 | 模型放错位置时无自动回搬，`corrections: []`，mechanical 策略必然 rc=1 |
| 3 | **恢复不做能力判断** | `fault_recovery.recover_artifact` 对同一 error 文案逐策略重跑 3 轮；`bounded_generation.run_paged_recovery` 每轮都先展开容量分层索引 | 一次字段级缺口 → 3 ×（40+ 分片 worker）；今日日志"未修项（有意识保留）"已点名此点 |

## 五、建议

### 立即（不改代码）

第024章可人工修：把 5 个事件中 `详情` 内的 `涉及章节 / 发生地点 / 参与成员 / 重量级 / 分组 / 标签集` 提到与 `详情` **同级**（顶层），并删除 `详情` 内同名键，使其符合 `VALID_FIELDS["事件集"]`。改完重跑 `run_pipeline.py run`。

### 代码侧（按性价比排序）

1. **反向搬迁**（解故障 B 类，收益最高）
   在 `relocate_element_fields` 增加「详情 → 顶层」分支：**仅当**顶层缺失该字段、且详情值类型符合该字段的顶层契约（如 `重量级` 为 0–100 的 int）时搬迁；顶层已有同名值时保留两处并记录（沿用现有冲突语义，不静默覆盖）。

2. **同错熔断**（解放大器，收益高、改动小）
   `recover_artifact` 在切换策略前比对"本轮 error 文案与上一轮是否逐字一致"；连续 2 轮一致即判 `REPAIR_EXHAUSTED`，跳过后续策略与容量分层索引，直接留断点。
   —— 这正是今日日志「未修项」中预留的方向："让恢复先判断模型是否具备修复能力，不具备就早停而不是跑满三策略"。

3. **校验对齐**（可选，长期防复发）
   `story_schema_rules.py:336` 在 `mode == "process"` 且键名命中 `VALID_FIELDS[collection]` 时降级为 warning，并提示"该键应位于顶层，可被程序搬迁"，与 `missing` 一侧对称。

> **红线提醒**（沿用项目既有教训）：以上第 1、3 条都属于"放宽/对齐 process 阶段策略"，实施前必须先核对**同字段在同阶段的既有模式策略**，且不得把 `final` 阶段的强制要求放宽。

### 验证方式

```bash
cd engine && ../runtime/venv/Scripts/python.exe -m pytest tests -q   # 当前基线 584（583 通过 / 1 跳过）
```

新增回归建议：
- 详情内 `int` 型标准字段（`重量级`）可被搬迁到顶层且不损坏叙述；
- 同一 error 文案连续两轮不变时提前熔断，不再展开容量分层。
