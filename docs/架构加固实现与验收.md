# 架构加固实现与验收

基线提交为 `72c8e7a`，在上一版治理契约、名称匹配与治理事务修复之上实施。目标是降低重复执行、让中断可恢复、减少界面扫描；不降低分析质量要求，不修改最终分析文档和故事结构的交付格式。

## 实现范围

| 问题 | 本轮处理 | 恢复边界 |
| --- | --- | --- |
| 普通章节先修改正式结构，再尝试回滚 | 合并、规范化、标签处理、校验、差异记录全部对候选文件执行；全部成功后原子替换 | `.commit.json` 保存产物摘要；发布前中断重做本地提交，发布后中断补齐进度，不重复合并 |
| 终稿修复的外层、内层重试相乘 | `repair_final` 进入统一修复预算；流水线与工作台均传入相同总额度；耗尽返回 65，外层停止再派发 | 用户明确继续或重试开启新额度；保留草稿和修复历史，不从整本书重做 |

| 每次找下一章都解析已验证的大快照 | 缓存成功验收结果，文件路径、大小、修改时间或创建时间发生变化即失效 | 首次和文件变化后仍执行验证；缓存仅在进程内，不替代磁盘证据 |

提交凭据和分包缓存只作为内部恢复材料，位于现有项目目录；正式故事 JSON 和分析 Markdown 不新增内部控制字段。历史没有提交凭据的章节继续按原验收规则读取。恢复凭据的 `published` 只在进度更新之后置为真，避免进度保存失败后被误跳过。

## 验收方式

全程使用本地假 worker、临时项目和故障注入，没有调用真实模型，没有重新运行《斗破苍穹》或《我独自升级》。此前两本书失败数据的离线验证结论见《治理可靠性修复与离线验证》。本轮没有重新修改书籍目录。

新增测试覆盖：五个本地提交步骤失败、正式结构发布前后中断、进度保存中断、快照缓存失效、终稿传输重试的总预算、工作台终稿入口、两个 worker 入口共享并发上限、排队取消和异常释放、成功分包复用与损坏/输入变化/强制重跑失效、失败分包不复用、长分析全文覆盖、worker 返回前日志已落盘、刷新突发事件的合并及无事件时不轮询。

旧分包测试原先使用 50 字符总预算，无法容纳完整契约，现改用足量材料和可用预算验证实际分包。并发集成测试增加等待执行线程进入的同步条件，不再将数据库中的 `running` 标记当成线程已经进入适配器的证明。

最终结果：引擎完整回归 347 项、后端完整回归 182 项、桌面回归 36 项全部通过，共 565 项。Web/Node TypeScript 检查和 Electron/Vite 构建通过。后端仍有原有 Starlette/httpx 的弃用提示，不影响测试结果。

## 适用范围与剩余边界

保留现有 Electron + Python + SQLite 的单体分层结构，没有增加微服务或消息中间件。本轮主要补强事务、有限重试、检查点、准入和事件刷新，不能据此承诺模型不会输出错误，也没有进行真实模型延迟基准测试。

全书汇总仍使用现有 reduce 流程，超大规模 partial 汇总的分层归并需要单独设计。原文抽样配置、其他背景材料的既有摘要策略没有改为新的内容删减策略；本轮解决的是章节分析正文截断及全书材料分包。单章结构/视觉任务的独立分层拆分、跨应用进程的并发协调不在本轮实现范围。

当前仓库没有独立的资料问答、借鉴智能体实现；本轮共享 worker 机制可以复用，但不宣称已经改造这些不存在的模块。代码测试与桌面构建不等于已经重启、安装或运行实际书籍任务。

## 2026-10-11：容量与治理分阶段加固

此节记录后续增量改造，前面的测试数量为当时的历史记录。

1. 统一请求容量预检：完整已声明材料去重计量，保留容量报告；超过预算返回 64，不截断证据，也不重复执行同一请求消耗语义修复策略。CLI 内部后续工具读取仍无法完整观测，报告明确标注估算而非真实 token 用量。
2. 单章局部修复：程序规范化先行；缺失提取理由与已确诊的名称错误可由模型只返回字段补丁。程序限制可写路径、校验原件摘要，再执行原有完整校验与独立复核。普通章节与治理仍使用各自原有验收模式。
3. 周期治理：按容量拆连续区间，子区间通过后再做跨区间复核；不能把子区间通过等同于父区间完成。重放时先应用子区间，再应用父区间的跨区间补丁。
4. 全书终稿：完整原文、分析、Delta、治理修正及故事结构进入材料目录；完全相同的文件共用一份读取材料，但保留来源角色。超大任务分批读取，模型输出现有治理 Delta，由程序合并到私有候选。真实结构修改须独立复核，最后仍执行原有严格终稿校验；全部通过才原子替换草稿。

### 容量配置

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `ND_CONTEXT_INPUT_TOKENS` | 300000 | 输入上限 |
| `ND_CONTEXT_OUTPUT_TOKENS` | 64000 | 输出预算；CodeBuddy 显式输出请求不得超过它 |
| `ND_CONTEXT_CONTEXT_TOKENS` | 300000 | 输入与输出共享窗口；只有提供方明确独立计量时才设为 0 |
| `ND_CONTEXT_RESERVE_TOKENS` | 30000 | 系统提示、工具和估算误差的预留 |

使用已有失败数据与已有修复候选离线验证：《斗破苍穹》先由程序归位 41 处字段，再局部补齐 11 条缺失理由；《我独自升级》仅修正 1 个已确诊名称。两例均通过原有 Delta 校验与内容保全检查。全书回放使用模拟“无需修改”输出，验证严格拒绝、全文材料覆盖及再次运行不重复请求；这不代表已经验证真实模型的全书语义质量。没有重新运行两本书或请求真实模型。

本轮引擎完整回归 436 项、后端完整回归 183 项通过；最终容量报告入口调整后，终稿治理 14 项针对性测试再次通过。后端保留原有 Starlette/httpx 弃用提示。额外覆盖合法合并后的档案保全、历史材料篡改恢复、严格失败不发布、模型/契约变更使检查点失效、程序规范化先于模型重试。

## 超大单章与全书报告的容量分层

### 职责与数据保全

`capacity_tree.py` 负责连续材料分片、节点检查点、容量自适应与有限重试；`bounded_generation.py` 对接章节分析、章节 Delta、修复材料和报告汇总。章节理解与结构化提取仍为两个独立步骤，最终依旧由原有章节提交与治理入口校验，不能用树节点通过替代业务校验。

- 单章内部片段仍属于原章节；程序合成一个十节分析 Markdown 和一个原格式 Delta，不增加虚假章节，不改变五章治理边界。
- 历史故事结构及最近十章完整 Delta 全文保留，超限时分批阅读并形成有来源位置的关联索引。索引服务于跨片判断，不能替代原件作为事实证据。
- 单章及报告的叶子正文完整保留，上层只增加跨区间判断，最终由程序按标题层级或原 JSON 结构合成；不会反复用短摘要替换已有正文。
- 正式名称相同的元素才确定性合并。只有本章明确新增的同名条目，才允许吸收其他片段对该新元素的修改；未知修改名称继续交原校验器，不能把拼写错误偷偷转为新增元素。
- 字符串正文和证据保全；不能直接合并的元数据标量由模型只裁决该字段，原值与依据保留在内部记录，禁止程序无依据覆盖。
- 全书汇总按目标文件分别组织，所有候选通过现有格式检查、输入版本核对后才逐个原子发布。中断后复用已完成的树节点；这不等于跨多个文件的一次文件系统事务。

### 调度与恢复

普通材料仍走现有路径。声明了分层材料的全书任务，在输入超限或预计单次输出风险较高时进入树；章节分析/Delta 超限时进入单章树。提供方返回 64 时保留容量语义，不再误报用户取消；130 才是取消。

容量错误才继续二分原材料，超长不完整 JSON 也保留原响应后尝试缩小片段。普通协议/语义错误每个节点最多三次，逐次改变修复指导；第三次可使用已有 `ND_RECOVERY_COMMAND`。节点预算、成功摘要和拆分决定持久化，重启不重置次数。传输异常不触发无限分片。父任务在 worker 并发准入之外选择分层路径，避免父任务占住名额再等待子任务。

超大的修复/复核材料先独立分页组织，再执行原来的限定修复和独立复核；程序优先、可写字段限制、内容保全和发布前版本核对保持有效。分层概览、覆盖区间、重试记录和原始失败响应仅是内部材料，不进入正式 Markdown/故事 JSON。

### 本轮离线验收与限制

使用两本书已经保存的第 7/8 章原文、分析、失败前故事结构和既有修复候选，模拟模型返回候选分片。合成 Delta 通过原 process 校验与原候选内容保全检查；再次执行已完成节点没有新增模拟请求。已有章节分析经分层合成仍通过十节结构校验，正文和表格逐行保留；报告回放同样核对原分析的全部非空行。没有调用真实模型，也没有重新运行书籍任务。

自动化测试还覆盖全文连续区间、跨层恢复、JSON/Markdown 格式、元数据冲突裁决、未知修改名称、容量返回码、原件保护、失败预算不重置、多目标失败不提前发布和修复材料分页。治理回滚集成用例显式选择 manual，仅检验真实程序回滚，不再等待离线防护拦下的提供方恢复尝试。

本轮引擎完整回归 446 项、后端完整回归 183 项通过；随后新增及调整的容量/故障恢复/提供方协议专项 85 项、检查点专项组合 31 项、最终容量与任务包/章节范围专项 43 项通过（这些专项彼此有重叠，不累加为独立测试总数）。后端仍有原有 Starlette/httpx 弃用提示。

容量树增加的是在受限窗口内继续处理的能力；超大任务可能需要更多模型调用，尚未测量真实延迟与语义质量。CLI 内部工具读取用量仍不可精确观测。若最小契约加运行开销都装不下，或模型连续输出不合格、服务持续不可用，仍会保留检查点并停止；不会通过删除内容、降低标准或无限重试冒充完成。

## 统一模型容量设置与任务隔离

设置页新增输入上限、单次输出上限、总上下文窗口、安全预留（均为 Token），以及单次调用超时（秒）、失败重试次数。字符分包参数保留并明确单位，不再以“上下文预算”混称模型窗口。默认输入 300000、输出 64000、共享窗口 300000、安全预留 30000，可用输入为 206000。单次输出上限必须能容纳最大的单个产物（例如包含思维链的单章 Delta），过小会导致长输出在输出侧被截断。公式为 `min(输入上限, 总窗口 - 输出上限) - 安全预留`；总窗口为 0 仅表示提供方明确拥有独立输入和输出额度，此时为 `输入上限 - 安全预留`。

前端实时预览并阻止保存空值、非整数或无可用输入的组合；后端将局部更新与已保存值合并校验，在同一数据库锁和事务内保存。任务不会读到一半新、一半旧的配置。配置固定于任务开始，运行期使用上下文变量，章节并发线程显式继承；内部打包脚本和模型子进程接收独立环境副本，不修改共享进程环境。已启动任务不受保存设置影响，全流程队列保留入队时配置；工作台尚未启动的任务在开始时读取快照。不同容量使报告检查点失效，避免复用不符合新策略的结果。

超时和调用失败重试沿用原有参数传递；零重试仍可保存，表示首次调用之后不做该层重试。语义恢复、分层节点与最终治理有自己的持久化有限策略预算，继续保持单一重试负责人，不把调用重试与语义重试相乘。小容量触发既有分层入口，不改正式产物格式，也不修改宽松章节校验与严格治理校验。

### 各阶段实际上读取什么

| 阶段 | 上下文组成 | 大材料处理及边界 |
| --- | --- | --- |
| 章节分析 Markdown | 本章完整原文、分析要求、十节格式约束 | 超大单章连续分片，保留叶子正文并由程序合成原格式；常规分析并不附加全部历史故事 |
| 章节 Delta | 本章原文、本章完整分析、故事历史、正式名称及输出契约 | 小故事内嵌全文；大故事常规路径使用完整名称索引、最近十章完整 Delta 和完整故事文件入口。超限路径分页阅读历史形成来源索引，再处理本章；索引不是历史正文的等价替代 |
| 每五章治理 | 当前周期完整原文、分析、Delta，上次治理记录、分类体系、历史故事 | 先尝试全故事，随后改为名称索引加相关档案、名称索引；周期证据不截断。仍超限则按章节区间拆分，子区间完成后做跨区间复核。最小单章治理包仍放不下时会明确失败，不能宣称任何窗口都能继续 |
| 全书分析及报告 | 故事名称索引、目标档案、各任务规定的章节分析/Delta 或全书结构材料、输出契约 | 先分包分析，再按目标文件逐层汇总；保留叶子结果和上层新增判断，程序合成完整产物。结构类任务使用故事结构/梗概等全书资料及文件入口，不等于每种报告都重新通读全部章节原文 |
| 最终全书治理 | 隔离候选故事、完整材料副本、分片证据、全局名称索引、已接受修改和严格整理要求 | 分步补丁与局部复核后再做全局一致性复核、原严格终稿校验；成功才允许发布 |

### 2026-10-12：无进展超时与回执版本门禁

本轮针对"总是卡住"和"改了上游却不生效"两类现象补齐两条判据。原则是**只收紧、不放开**：新增判据只会更早终止零进展的执行、更严格地复查旧结论，不会重跑已完成章节、不会重新生成任何产物。

#### 一、无进展（idle）超时

墙钟超时按"总共跑了多久"终止，会连正在长时间生成的请求一起杀掉；本轮增加一条按"还有没有进展"终止的独立判据。

| 位置 | 判据 | 返回码与恢复 |
| --- | --- | --- |
| `stream_shell_command`（隐藏窗口，所有 provider） | 连续 `idle_limit` 秒没有任何 worker 输出 | 124，上层立即重试/切换 provider |
| `run_structured_stream`（CodeBuddy 流式路径） | 连续 `idle_limit` 秒没有任何**流事件** | 124，`main()` 在同一次调用内换下一个 provider，不必等外层墙钟 |
| `run_visible_powershell_command`（可见窗口，非 keep-open） | 连续 `idle_limit` 秒日志文件不再增长 | 124，同上 |

- 上限 `ND_WORKER_IDLE_TIMEOUT`，默认 900 秒，下限 60 秒，且不超过墙钟超时（`min(上限, 墙钟)`），设 0 表示关闭、只保留墙钟判据。
- 默认 900 秒的取值有实测依据（下节），不是估计值。
- 心跳行与进程存活提示是自己打印的，**不算进展**，因此不会掩盖真正的卡死。
- 终止时输出"连续 N 秒无输出（无进展）"并附"本次最长无输出窗口"，与"命令执行超时"两种诊断可区分；本次最长窗口会写进 worker 日志，便于按自己机器的真实数据调 `ND_WORKER_IDLE_TIMEOUT`。
- `keep-open` 模式命令结束后仍在等用户按键，静默属正常，故该模式不启用此判据。

取值依据（`拆书_斗破苍穹/质量治理/worker日志`，10-11 至 10-12 共 335 份 worker 日志）：

| 观测 | 数值 | 含义 |
| --- | --- | --- |
| 健康任务最长合法无输出窗口 | 约 600 秒（`delta_ch012` 单轮长生成） | 上限必须高于它，否则误杀正常生成 |
| 真实卡死 | 全程零输出并撞满 1200 秒墙钟（`audit_correction` 两次 1171 秒） | 有明确的"零进展"形态可以判 |
| 卡死后紧接着的成功尝试 | 150 秒 | 卡死不是任务本身需要长耗时 |
| 同任务的健康会话内部日志最大静默间隔 | 30 秒（9 份会话） | 有细粒度存活信号，但仅用于说明 CLI 自身在跑，不作为本判据阈值 |

因此 900 秒高于已知合法窗口、低于墙钟，既不误杀又能比墙钟早收手；它同时也是"这次失败到底该不该重试"的判据——零输出永远不该继续等。

#### 二、提交回执的版本门禁

`*.commit.json` 的含义是"这份产物在**某个版本的程序**下通过过"。程序之后收紧校验、修好纠错或改了结构规则后，旧回执不再能证明当前程序也会接受它。

- 新增 `engine/scripts/engine_contract.py`：对**决定"什么算通过"的文件**做内容指纹（`schemas/*.json` + `validate_delta/validate_structure/validate_chapter_analysis/coerce_delta/compress_tags/normalize_story_schema/story_schema_rules/registered_types/governance_contract`），删除文件同样改变指纹。
- 提交回执写入 `contract` 字段；`receipt_shortcut_allowed` 要求"产物摘要一致**且**契约一致"才允许免检放行。
- 跨版本时只放弃捷径，回落到 `is_chapter_complete` 的完整复验（重跑结构校验并核对校验报告状态）。**不重跑模型、不重新生成、不改写进度**，也不会把已完成章节判为未完成。
- 缺少 `contract` 字段的历史回执一律按跨版本处理。首次跑新版时，每章的免检捷径失效一次，代价是章节阶段多验一遍结构；这是有意的，避免"上游修好了但旧回执继续放行"。
- 提示词（`prompts/*.j2`）**刻意不纳入**契约指纹：改提示词不应让历史回执全部失效并触发大规模重算；提示词相关性由容量分层/分包检查点按内容哈希负责，它们本来就是内容寻址的。

### 2026-10-12（二）：周期治理 `介绍.标题` 契约冲突修复

**现象**：《斗破苍穹》周期审计 011-015 治理补丁连续三次被判不合格（返回码 65），自动恢复依次用完 mechanical / targeted / evidence / diagnosed 四种策略后停在"保留证据与断点"，整条流水线中止。恢复过程共拉起约 25 个 `bounded_fragment` worker、耗时约 31 分钟，最终仍返回 65。

### 2026-10-12（三）：故事简介篇幅契约（500 字）

**触发**：用户提出"每五章生成一次故事简介，章节多了简介会不会太长？是否该单独做一个生成功能并控制在 500 字以内？"

#### 一、实测：会变长，且当时没有任何上限

从《斗破苍穹》`故事结构版本/` 的实盘快照逐周期取 `介绍.描述` 长度：

| 时点 | 长度 | 变化 |
| --- | --- | --- |
| ch005 后治理（首次生成） | 0 → 257 | — |
| 011-015 周期治理 | 257 → 376 | +119 |
| 016-020 周期治理 | 376 → 510 | +134 |

每周期约 **+120~134 字**，方向稳定、无任何上限。3620 章即约 724 个周期，简介会持续变长。程序侧不存在任何篇幅判据：`story_schema_rules` 的 `final` 模式只要求描述**非空**。

#### 二、根因：同一个字段被三处用不同尺度对待

| 环节 | 位置 | 对简介的尺度 |
| --- | --- | --- |
| 生成端 | `prompts/流水线/周期审计.j2` | "更新为覆盖当前已处理故事的一份连贯简介"——**无字数要求** |
| 归并端 | `governance_introduction.combine_introductions` | 预算阶梯 **2000 / 1000 / 500 / 250** 字 |
| 消费端 | `analysis_context_pack.summarize_story_structure` | 只把描述前 **500 字**放进任务包（`[:500]`） |

三处不一致的直接后果：简介在生成端被允许写到 2000 字量级，而下游任务包**永远只读前 500 字**。超出的部分不产生任何作用，却仍然占用故事结构体积、每轮输入预算、每周期一次的生成输出，以及每一份章节快照的复制成本。同时 `单章增量提取.j2` 的字段示例里还写着"可以写长一点"，是方向相反的历史指令（实测章节 Delta 未输出顶层介绍，尚未造成实际叠加，但属隐患）。

**为什么不需要"单独的生成章节简介功能"**：病根不是"生成动作放错了位置"，而是这个动作**没有篇幅契约**。周期治理本就承担顶层介绍治理职责，是对齐周期边界的正确位置；把简介生成拆成独立调用链只会新增失败点、新的恢复路径与新的断点语义——与"越改越有问题"的既有判断相悖。加契约即可，不动结构。

#### 三、方案（生成端约束 + 三处对齐，零新增调用链）

- 新增 `engine/scripts/synopsis_contract.py`：`SYNOPSIS_MAX_CHARS = 500` 与归并阶梯 `SYNOPSIS_SYNTHESIS_BUDGETS`，作为生成端、归并端、消费端的**单一事实来源**。
- `prompts/流水线/周期审计.j2`：写入篇幅契约——"简介篇幅有硬性上限 500 字（含标点），这是契约不是建议：已处理章节变多不等于简介变长，新增内容必须靠压缩既有表述换取，不得逐周期累加。简介是给读者的入口而不是索引，细节由角色/事件/地点/线索/阵营/物品档案承载"。**这一层才是真正约束模型的地方。**
- `governance_introduction.py`：归并阶梯改为引用契约（首档即 500，超出输入预算时收紧到 400/300/200），并在归并指令里明确"这是替换旧简介的完整新版，不是追加"。
- `analysis_context_pack.py`：`[:500]` 改为 `[:SYNOPSIS_MAX_CHARS]`，消除魔法数与漂移。
- `单章增量提取.j2`：把"可以写长一点"改为"顶层故事简介由周期治理统一生成并整份替换；单章增量通常留空"，元素级档案的"可写长字符串"保持不变。

**刻意不做程序侧篇幅门禁**（软契约）。周期治理属 process 阶段，按既有模式策略过程阶段不得把内容问题升级为 error；把它做成硬门禁会立刻重演 `介绍.标题` 那类死锁（模型"写短"与"写全"两边都做不到，然后修复策略全败）。`test_overlong_synopsis_is_never_a_periodic_failure` 把这条红线锁进回归。

**刻意不把 `synopsis_contract.py` 纳入 `engine_contract` 指纹**：篇幅是软契约，调字数不应让历史回执集体失效并触发大规模重算（`test_char_budget_is_not_a_validation_fingerprint` 锁定）。

#### 四、验证

- 新增回归 6 项：周期提示词含篇幅契约且既有语句未被挤掉；章节提示词不再含"可以写长一点"且元素级保真语句仍在；预算与上限同源且归并阶梯不超上限；下游实际读取正好等于契约值（构造 800 字描述，断言任务包里只出现 500 字）；超长简介不判失败；常量模块不在校验指纹内。
- 引擎完整回归见本节测试汇总；真实模型调用 0。

#### 五、如实说明：这次改动省的是什么

- **省的是长期退化成本**，不是立刻提速：下游本来就只读 500 字，所以截断行为现在与将来一致；收益在于故事结构体积、每周期输出、快照与输入预算不再随章节数无界增长。
- **生效时机**：程序不主动改已有简介，只有下一次周期治理（模型按新契约重写）才会把当前 510 字压回 500 以内。
- **未做的观测项**：如果没有篇幅告警，模型偶尔写到 600~800 字时不会有人知道（超出部分被下游静默丢弃，浪费有限）。本轮判断"多加一条警告"的边际价值低于它被既有 14~27 条"缺少标准字段"警告淹没的风险，故不加；若后续观察到持续超长，再考虑加可观测性。

### 2026-10-12（四）：详情→顶层反向搬迁（修第024章类卡死）

**现象**：第024章章节 Delta 连续被判不合格（返回码 65），自动恢复用完 targeted / evidence 等策略后中断，流水线停在 ch024（20:39 之后再无产出）。

#### 一、根因：程序侧对"字段放错位置"只有单向出口

模型把**事件集的标准顶层字段整组写进了 `详情`**，顶层只剩 `名称 / 时间`：

| 位置 | 内容 |
| --- | --- |
| 顶层 | `名称`、`时间` |
| `详情` | `涉及章节`、`发生地点`、`参与成员`、**`重量级`(int)**、`分组`、`标签集`(字符串)、`动作链条`、`提取理由` … |

`story_schema_rules.py:336` 判定 `详情` 的值只允许 `string` / `string[]`，而 `重量级` 是 `int` → **10 条硬错误**（5 个事件 × 2），全部同型：

```
新增元素.事件[…].详情[重量级] 值类型必须是 string 或 string[]，实际为int
```

而这些字段本该在顶层，顶层缺失它们只产生 **warning**（“normalize 将补齐默认值”）——同一件事，一侧可自愈、一侧致命。

**为什么程序修不了**：`coerce_delta.relocate_element_fields` 是**单向**的（顶层 → 详情），`重量级` 的强制转换分支只看顶层 `item["重量级"]`，`normalize_story_schema` 只补顶层默认值、不清除 `详情` 内的多余键。→ 该错误**在程序侧没有任何消除路径**，只能反复丢给模型重写，而模型连续三轮都没改变组织方式（账本实测 `{"corrections": []}`），放大成整份容量分层的多轮空转。

与 10-12 的周期治理 `介绍.标题` 事故**结构同构**：都是"校验器在过程阶段拒绝 + 程序侧无自动修复能力"。

#### 二、修复：`relocate_element_fields` 增加反向分支（+44 行，1 文件）

**仅当**同时满足以下条件时，把 `详情` 里的原值搬回顶层并删除 `详情` 内同名键：

1. 该键名是该集合的**合法顶层字段**（`VALID_FIELDS`）；
2. 顶层**缺失**该键（顶层已有同名值时，`详情` 内副本原样保留，不覆盖）；
3. 值的**类型符合该字段的顶层契约**——以 `DEFAULTS` 为单一类型来源（`int` / `str` / `list[str]`，`bool` 必须先于 `int` 判定，否则 `False/True` 会被当成 `重量级`）；
4. 值**非空**（空串/空数组不携带信息，搬上去只会掩盖"缺少标准字段"的 warning）；
5. 排除 `名称`——正式名称由 `align_registered_types` 身份对齐负责，不能从 `详情` 里的同名叙述键推断。

**只搬运、不发明**：不改变文本、类型或列表内容；类型不符就不搬，留给校验器报错（例如 `详情.标签集` 是字符串时**保持原位**，因为顶层契约是 `list[str]`）。

**刻意不做**：没有把 `story_schema_rules.py:336` 在 process 阶段降级为 warning。既然反向搬迁已经在 coerce 阶段（先于校验）消除该错误，再去放宽校验只会削弱 `final` 交付标准，属于没有必要的放开。

#### 三、验证（真实工件，零真实模型调用）

1. **纯函数层**：对磁盘上那份真实的 ch024 Delta 直接调 `relocate_element_fields` → 46 处搬迁（5 个事件 × 4 字段 + 其它集合），`重量级` 在 `详情` 中零残留。
2. **提交链**：工程副本上 `commit_chapter(proj, 24)` → **rc = 0**，合并 / 规范化 / `validate_structure --mode process` / diff 全链路通过（此前从未走到这一步，反证唯一阻塞点就是这里）。
3. **真实恢复入口、零模型调用**：全新副本上 `run_repair_worker("", proj, "repair_chapter", …)`（**命令为空**，即不允许调用任何模型）→ **rc = 0**，日志 `自动恢复：修复验收通过，继续流水线 {'strategy': 'mechanical'}`。账本转为 `generation=2 / status=succeeded / mechanical.returncode=0 / attempts=[]`——**完全没有进入模型策略阶梯**。

#### 四、一次被回退的改动（如实记录）

本轮先实现了"连续多轮无进展即提前停止"的熔断（拟用于压制容量分层的重复展开），随后**完整回退**。原因：`recover_artifact` 的既有契约是"**一次调用走完整条修复策略阶梯**"，且这条契约被 9 个回归用例显式锁定（`test_switch_strategy_validate_then_publish_once`、`test_diagnosis_strategy_and_configured_model_fallback`、`test_diagnosis_protocol_retries_once_then_continues`、`test_invalid_diagnosis_exhausts_bounded_budget_without_publication` 等，均要求"前一策略失败后仍继续下一个"）。在该契约下，任何"止损"都等于削减恢复能力，与"尽量不出错、尽量不需要介入"相冲突。

**代价是**：恢复路径仍会为**内容级**缺口按策略重建整份容量分层（真实案例：约 43~54 份只读材料 × 每个策略）。本轮只把"程序侧能修"的这一类彻底消除，没有再动阶梯。若之后确实需要压这块钱，正确方向是**让容量分层的证据索引跨策略复用**（按材料内容寻址，而非按每次尝试的临时路径寻址），而不是减少策略数量——后者会直接削弱恢复能力。

#### 五、可操作性的小改进（零逻辑风险）

`recover_artifact` 真正用尽策略时，除原有事件外再打印未修复产物路径、恢复账本路径与最后一轮失败反馈路径，让"停下来"这件事可操作，无需翻日志猜原因。

### 2026-10-12（五）：简介上限 500 → 1500 字，并固定为四分节结构

**触发**：用户要求"简介放开到 1500 字的限制，然后结构化展示"。本节**取代**（三）里的 500 字契约，（三）作为历史记录保留。

**问题**：《斗破苍穹》3620 章的规模下，500 字上限对"读者入口"而言太窄——简介必须一直靠压缩既有表述换取篇幅，越到后期越写不出主线层次；而现有简介是**一整段连续长文**，在纯文本查看器里没有层次感，读起来是"一坨"。篇幅上限调整本身只是改一个数字，真正需要设计的是"1500 字该长成什么样"。

#### 一、变更清单

| 位置 | before | after |
|---|---|---|
| `engine/scripts/synopsis_contract.py` | `SYNOPSIS_MAX_CHARS = 500` | `= 1500` |
| 同上 | 无结构定义 | `SYNOPSIS_SECTIONS = ("主线","主角处境","核心冲突","当前进展")`，配 `synopsis_section_headings()` / `synopsis_section_spec()` |
| 同上 | `SYNOPSIS_SYNTHESIS_BUDGETS = (500,400,300,200)` | `= (1500,1100,700,400)` |
| `prompts/流水线/周期审计.j2` | "硬性上限 500 字" | "硬性上限 1500 字" + 分节结构硬要求 + 未结构化旧简介必须重写的触发条件 |
| `scripts/governance_introduction.py` | 归并指令只约束字数 | 追加 `_SECTION_RULE`，分节定义从 `synopsis_contract` 单一来源读取 |
| `tests/test_periodic_introduction.py` | 18 项 | +2 项（提示词分节要求、分节单一来源），并把预算断言改为 1500 + 严格递减 |

`analysis_context_pack.summarize_story_structure` 无需改动：它读 `SYNOPSIS_MAX_CHARS`，自动从截断 500 字变成截断 1500 字（消费端与生成端仍然同源，这正是当初把上限做成单一常量的目的）。

#### 二、结构形态：`【小标题】` + 空行分段，不用 Markdown

格式约定：四个分节标题各占一行写在段首，正文接在标题之后，节与节之间空一行。

```
【主线】……（整体脉络）
【主角处境】……（主角当下位置与状态）
【核心冲突】……（当前最主要的张力与对手）
【当前进展】……（已处理到最后一个章节的处境）
```

**为什么是 `【】` 而不是 `**加粗**`**：`介绍.描述` 是一个**纯文本字符串字段**，能被纯文本查看器、JSON 原文、Obsidian 导出三条路径读取。Markdown 标记在需要渲染的那一条路径上才有意义，在另外两条路径上是**字面噪声**（读者会看到多余的星号）。`【】` 是中文排版里既有的分节约定，三条路径下都可读，且不与其他语法冲突。

**为什么不做程序侧门禁**：篇幅与结构都是**软契约**，与本目录 README 的"过程阶段不升级为 error"原则一致，也与（三）里 `test_overlong_synopsis_is_never_a_periodic_failure` 锁定的既有模式策略一致。若在 process 阶段要求"描述必须含四个分节"，模型一旦漏写一节，就会重演标题门禁那类死锁（模型在"写全"与"写短"之间两边都做不到）。因此约束放在**真正约束模型的那一层**——生成端提示词与归并指令，并把这条耦合用测试锁住。

#### 三、一个容易漏掉的失效模式

提示词原本只要求"简介为空 / 主线变化 / 旧简介失真"时才更新。若只改字数与结构要求而**不动更新条件**，模型完全可能判定"现有 510 字旧简介内容准确、无需更新"，从而**永远保留那一整段无结构旧简介**——用户就永远看不到结构化效果。

因此新增显式触发条件：**旧简介未按分节结构组织时一律视为需要更新**，必须整份重写，"内容准确"不构成跳过的理由。这条是让改动真正生效的关键，已写入提示词并由回归用例锁定（`assert "一律视为需要更新" in text`）。

- 预算断言从 `== 500` 改为 `== 1500`，并补"阶梯必须严格递减"与"分节标题不得吃掉过多预算"两条不变量。

#### 五、影响面（与历史回执/恢复账本的关系）

- `SYNOPSIS_MAX_CHARS` 所在的 `synopsis_contract.py` **不在** `engine_contract._CONTRACT_SCRIPTS` 里，本轮也**没有**把它加进去：改字数与分节不应让历史提交回执集体失效。既有用例 `test_char_budget_is_not_a_validation_fingerprint` 继续守这条线。
