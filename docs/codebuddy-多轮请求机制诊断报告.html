一、结论摘要

  1. 日志中的「CLI 模型请求第 N 轮」不是重试，也不是多次分包。它是同一次 agent 会话内部，模型与只读上下文工具之间往返所产生的一次次真实模型调用，每出现一个新的请求标识即计一轮。
  2. 真实模型请求数 = 日志显示轮数 − 1。第 1 轮由会话标识占用，并非一次独立请求；该偏差来自计数表达式 _messageId or _requestId 的兜底顺序。

六、结论与建议

6.1 关于「多轮」的判定

多轮属正常且必要的行为，无需干预。冻结材料以只读 MCP 工具暴露给模型后，模型需要先枚举材料、再逐项读取，每次工具往返都构成一次新的模型请求；最后一轮才产出结构化产物。这也是任务包使用 --allowedTools 精确授权而刻意不设 --max-turns 上限的原因——agent_worker.py:169-172 的注释已说明：隐式的低轮数上限会在工具提交之前终止会话，产生空结果。

6.2 可选的观测性改进

当前计数表达式 value.get("_messageId") or value.get("_requestId") 会把会话 ID 计入轮次，导致读者把「5 轮」误读为 5 次模型调用。若希望日志更直观，可将会话标识与请求标识分列计数（例如输出「会话 x1，模型请求 N 次」）。此项属观测口径调整，不改变调度语义，亦不涉及契约指纹。

6.3 针对本次失败的环境级建议

本次失败已由自动重试闭环解决，代码侧无需改动。若要降低同类中断概率，可在长时间批量运行期间抑制系统待机：

  • 接通电源时将待机超时设为「从不」，例如在管理员终端执行 powercfg /change standby-timeout-ac 0；此为会话级或用户级电源设置，不触及项目配置。
  • 批量运行期间避免合盖，或在电源计划中将「合盖操作」设为「不采取任何操作」。
  • 本机 Intel Wi-Fi 6 AX101 在待机过渡期反复出现 Miniport Halt 与 DRIPS 设备重枚举，与已知的间歇断连现象一致；若需彻底规避，可在此基础上进一步排查驱动版本。
