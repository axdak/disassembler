# 治理可靠性修复与离线验证

## 范围与约束

本次修复针对周期治理、章节 Delta 的提示词冲突、名称匹配、合并规则、重复修复和断点恢复。不重新分析两本书，不调用真实模型，不减少章节分析维度、有效元素和档案内容，不迁移现有故事结构或 Delta 的对外字段格式。

章节列表的虚拟化、固定刷新按钮和手动刷新已包含在前置提交 `0432395`，不引入分页。本次后端修复不改变该交互。

## 已确认的共性原因

1. 单章提取提示词混入“创作故事”和最低元素数量要求，与忠实提取冲突。治理提示词又漏掉校验实际要求的章节范围、提取理由等约束。
2. 治理查找把正式名称与别名混在同一次顺序扫描中，互为别名的两个元素可能命中同一对象；普通章节合并还会把不存在的修改目标静默转成新增。
3. 引用替换遍历任意字符串，可能连元素名称和叙述一起改写；章节元数据、补充标签错误地采用普通字符串拼接规则。
4. 治理修复只收到原审计任务，没有本次错误和当前失败补丁。修复次数又受到内外层循环叠加影响；连续产生不同的错误文件时可能长时间反复调用模型。

这些问题会放大模型输出差异。更强模型可能更容易避开部分问题，但不能替代程序自身的正确匹配、提交与重试规则。

## 实现边界

- `element_identity.py` 统一正式名称优先、唯一别名次之的规则。冲突别名不取第一个；近似名称只给候选，不自动判定同一实体。普通合并、治理操作和引用规范化共用该规则。增量更新索引，避免每次修改都扫描整个集合。
- 未知修改目标在入库前报出。新增必须显式声明；修改允许继承已有章节元数据，但显式错误值和缺失提取理由仍受校验，合并后的完整结构仍须通过检查。
- 治理只重定向同类型的标准引用字段和明确的 `类型:名称` 引用，不改其他实体声明、跨类型同名对象和普通叙述。轨迹、补充标签按原 JSON 字符串数组格式去重合并；首次章节取最早、最近章节取最晚。任何操作失败都不提交部分结果。
- `governance_contract.py` 只做可逆的结构纠正：还原误序列化的对象/数组、规范明确的单个章节序号、从已知调度范围补齐缺失范围。保留原文件和变更记录，不伪造分析理由或证据。
- 原生结构化输出使用现有治理 schema。提示词仍保留完整分析与档案要求；缓存任务包通过模板指纹失效，升级后不会继续使用旧冲突提示词。
- 修复包包含当前失败产物、本次错误和原任务证据。`repair_budget.py` 在调用前持久化次数及失败副本，同一用户运行中的自动重派共享额度。默认章节修复最多 3 次、治理修复最多 2 次；传输失败也计入额度，形成修复循环时提前停止。返回码 `65` 表示本轮修复额度耗尽，外层编排不再重派。
- 用户再次继续运行会获得新一轮额度，保留以前的尝试记录和已完成产物。重试日志位于项目的 `质量治理/重试记录`。本次改动没有把已经完成的章节重新发给模型。
- 治理在临时副本完成合并、规范化、校验、快照和差异记录后，原子替换正式文件。提交凭据保存补丁与结构摘要；若在落盘后、标记完成前中断，恢复时核对摘要并补记状态，避免重复合并。流水线 JSON 状态也采用原子写入。

资料问答、借鉴等智能体应遵循相同的“明确输入输出、确定性校验、有界重试、保留产物”原则。本次没有重写这些智能体的业务流程，也没有声称已完成它们的全部容灾改造。
