建议的最小架构

宿主确定章节 / 证据 / 版本 / 预算
↓
CodeBuddy：读取原文和必要事实 → 批量提交候选变更 → 接收结构化校验错误 → 原任务内修正
↓
宿主：完整校验与必要复核 → 版本检查 → 原子发布 → 保存回执和断点

  • 事实只存一份。当前视图、索引和历史切片从权威 JSON 派生；可缓存但绑定版本。不先做全库格式迁移，不删历史来换速度。
  • 模型不直接写正式文件。领域工具限制集合、字段、章节和操作；复用现有 merge_delta / 治理规则，避免出现第二套合并含义。相关修改在候选中成组完成。
  • 完成由宿主认定。模型说“完成”不等于成功；宿主检查候选、证据覆盖、引用、保全、版本和回执。读不到或检索不到不能被当成“事实不存在”。
  • 读取可批量，提交有顺序。已有章节分析并行和 interleaved 可复用；依赖前章状态的 Delta、治理提交保持正确顺序。不以并行写正式结构换取表面吞吐。
  • 恢复靠数据记录。会话丢失后从候选和操作账本续接；不要求 CLI 记住所有历史。结果未知先对账，不能盲目重复应用。

故事家本地实现值得借鉴的是分级读取、软预算、写入版本条件与操作状态账本。无需先移植多套运行时适配器、完整多智能体体系或通用调度框架。

如何证明更快、更稳

优化目标是完整作业成功交付耗时和事实质量，不只是某一次模型响应时间。

  • 正确性：事实精确率、召回率、身份/类别/引用正确率、历史事实保全、审计漏检；用原文标注和固定案例判断，不能只比较 JSON 是否可解析。
  • 性能：记录中位数、P95、总请求数、累计实际输入/输出、修复占比；按普通章、复杂章、治理和故障恢复分别统计。扩大样本后再判断P95，13章历史样本不够支持稳定承诺。
  • 自动化：统计可恢复故障自动接续率、无效重试次数、每百章人工介入次数，以及已成功片段是否被重做。
  • 故障：覆盖断网/429/5xx、流无进展、输出截断、协议错误、MCP错误、进程终止、写后未回执、文件占用、磁盘满和版本冲突。
  • 对照：相同冻结输入、相同模型与推理设置，多轮重复；先验收语义不退化和数据不损坏，再决定上线。当前38%–45%的旧档案体积缩减实验只说明输入有压缩空间，不等于耗时或准确率已改善。

不建议现在简单调大并发、缩短所有超时、跳过周期治理、降低全部推理强度或无限重试。这些都需要对应的瓶颈与质量证据。可以自动处理的异常自动接续；真正证据冲突应保留候选与具体问题，不能为“无人介入”擅自猜写事实。
