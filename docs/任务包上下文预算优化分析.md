# 任务包上下文预算优化分析

> 状态:分析定稿,待排期(本文档只记录结论与方向,不含实施)
> 范围:`engine/scripts/analysis_context_pack.py`、`engine/scripts/orchestrator.py`
> 背景:源自对 Claude Code / OpenAI Codex / DeepSeek Harness 三家 Agent
> 上下文治理的源码调研(调研全文见 linestory 仓库
> `docs/分级阅读与上下文治理重构方案.md` 附录)。

---

## 一、现状评估:底子是先进的,方向不用改

当前任务包压缩体系(`RunConfig` 压缩策略字段 + `analysis_context_pack.py`):

| 层级 | 机制 |
|------|------|
| 分包 | 章节贪心装箱,单包 ≤ `max_pack_chars`(默认 70000 字符) |
| 全书级降载 | **三档 fallback:全量梗概 -> 分章梗概索引 -> 仅故事索引**,超预算降载而非硬截断(`build_structure_context`) |
| 章节级原文 | `auto/none/sample/full` 四策略;sample = 首/中/末三段各 1/3 预算(`sample_original`) |
| 章节级分析 | `max_analysis_chars` 硬截断 |
| 常驻上下文 | 每包带故事结构全名称索引(等价于"简报层") |
| 重试 | worker 10 次尝试、校验修复 3 轮、停滞 3 次判硬阻塞 |

**关键结论:三档降载已经实践了 DeepSeek Harness `tool-result-pruner`
的同一哲学(确定性降载优先于有损操作),且形态更优--降载是换信息密度、
保全覆盖率(分章索引仍覆盖每一章),不是砍内容。** 每个任务包内也已是
微缩四层金字塔:故事索引(简报)+ 章节块(按需)+ 分包(分页)+ schema
校验(机械层)。

另外,本项目是**无状态批处理**:每个包是独立 LLM 任务、上下文全新,不存在
对话历史累积。因此三家的**会话压缩方案对本项目不适用**(见第三节)。

## 二、值得补的三个缺口

### 缺口 1:预算全是字符,模型盲(优先级最高)

70000 中文字符 ≈ 45~55k token,`context_budget_chars: 160000` ≈ 100k+
token。换 64k 窗口的 worker 模型,现有阈值全部失真,且设置页只能靠人肉
重算。DeepSeek Harness 的解法可移植:**容量由适配层持有精确路由信息,
预算按窗口比例推导**。

方向:`有效包预算(字符) = 模型窗口(token) × 安全系数 ÷ 中文字符 token
比`。`max_pack_chars` 保留为人工上限,默认值改为从 worker 模型上下文窗口
推导;设置页展示推导结果而非要求用户自填盲值。

### 缺口 2:没有溢出恢复分支

现状:worker 撞上下文超限,重试的是**同一个包**,10 次都一样超,最终硬
阻塞。DeepSeek 的 `CONTEXT_WINDOW_EXCEEDED` 分支是现成答案:

1. 从 worker 输出识别上下文超限错误(错误码 + 关键字双通道);
2. `max_pack_chars` 减半重新分包(**只重分溢出的那个任务**,已完成 partial
   不动);
3. 恰好重试一次,以"分包结果确实变化"为证明,无变化透传原错误。

改动集中在 orchestrator 的重试判定与 analysis-pack 的重分包入口,救的是
"大书 + 换模型"场景下的整条流水线。

### 缺口 3:预算数学散落,计量无唯一 owner

`summary_budget = max(10000, max_pack_chars - 30000)`、
`budget = max(20000, max_pack_chars - OVERHEAD)` 等魔法常数分散在
`analysis_context_pack.py` 内多处。DeepSeek `dsh-token-meter` 的教训:
**计量与预算推导只应有一个 owner**,否则每加一个任务类型就多一处漂移的
常数。

方向:拆 `context_budget.py` 统一持有字符/token 换算、各档预算推导、
安全系数;设置页透传与 `build_structure_context`/`split_batches` 全部只
对接它。

## 三、明确不引入清单(防过度设计)

以下机制属于**会话治理**问题域,与本项目"无状态任务包输入侧预算工程"
不同域,引入即过度设计:

- 会话压缩 / 摘要结转(Codex compaction、DeepSeek compaction-basic)
- 常驻简报的版本与重生成(本项目每包现算索引,天然无陈旧问题)
- 读前校验 / If-Match 版本戳(无并发编辑,无"拿旧地图改路"风险)
- 历史归一化 / 孤儿配对(没有累积历史,无孤儿可言)

## 四、与 linestory 方案的双向关系

- **正向继承**:linestory 重构方案的"修剪器(降载不截断)"直接继承本项目
  三档降载哲学;其"常驻索引 + 按需详情 + 游标分页"即本项目"故事索引 +
  章节块 + 分包"的会话版。
- **反向反哺**:本文档缺口 1(模型感知预算推导)与缺口 2(溢出减半重分包)
  即调研结论向本项目的回流,实施时可直接参考 DeepSeek Harness 的
  `resolveModel` 容量解析与溢出恢复分支设计。
