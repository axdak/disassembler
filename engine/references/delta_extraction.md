# Delta 提取与合并规则

Delta提取器负责读取：当前故事结构(或摘要) + 章节原文 + 章节分析MD，并输出纯 JSON（本章增量）。

## 提取规则

1. **只输出本章Delta，不输出完整故事结构JSON**。
2. 新元素放入 `新增元素`，必须提供完整标准字段。
3. 已存在元素放入 `修改元素`，只填本章新增/变化字段，不要重写旧元素。
4. 通过名称和别名判断是否已有元素，别名不要当成新人物。
5. 每个 `新增元素` 和 `修改元素` 都必须在 `详情` 中提供非空 `提取理由`，用于 Delta 审计，说明该元素为什么值得提取或本章为什么更新它；最终故事结构只允许事件继续保留 `详情.提取理由`，角色、地点、线索、阵营、物品、其他事项会在合并时丢弃该字段。角色、地点、线索、阵营、物品必须在 `详情` 中提供 `首次章节`、`最近章节`；事件必须在 `详情` 中提供 `涉及章节`；`其他事项集`只要求公共字段，不伪造章节追溯字段。
6. 角色 `生日`、`是否主角`、`性别`、`年龄` 等机械字段由 `coerce_delta.py` 自动补默认值和类型转换，LLM 不需要填写。事件 `时间` 由脚本从 `详情.涉及章节` 自动推导，LLM 不需要填写。事件必须在 `详情` 中提供 `涉及章节`（章节号即可，格式归一化由脚本完成）。
7. 事件数组按最小涉及章节排序；治理新增历史聚合事件时按该位置插入，修改既有事件不得移动位置。事件分组使用 `8位段号-40字以内复合剧情段短名`，例如 `00000010-退婚尊严线冲突爆发羞辱反击身份尊严`；短名需压缩包含剧情、剧情线主题、叙事功能、爽点/情绪点、冲突悬念类型。同一完整分组只能覆盖同一章节内的连续事件区间，治理后按事件数组顺序重排全部8位段号。
8. 跨章节主线、主题、功能、爽点和冲突悬念可按原文价值写入普通标签或后续全书分析，不作为逐章 Delta 的硬分组结构。正式线索关联写入 `详情.关联线索`（例如 `线索:退婚约定`）。视觉资产入口写入 `标签集`，具体画面生产资料写入 `详情.视觉等级`、`详情.画面类型`、`详情.核心画面`、`详情.镜头建议`、`详情.氛围`、`详情.视觉理由`、`详情.视觉用途`。
9. 不确定信息不得写成确定事实，应放入 `详情` 中的“疑似信息/待确认信息”一类字段，或写入 `冲突声明`。这类长期累计字段推荐使用 JSON 字符串数组，便于追加去重，例如 `"疑似信息": "[\"身份疑似镖师；来源:第003章\"]"`。若原文提到亲属、师徒、仇敌等关系，但目标人物尚未正式入库，不要把它写入角色 `关系` 数组；先保存在 `详情.关系线索`，例如 `"关系线索": "[\"父亲:郭巨侠；来源:第003章；目标角色未正式入库\"]"`。该信息落盘后作为档案长期保留，不要求自动回补；只有目标角色已存在或本章确需新增为正式角色时，才写成结构化 `关系`。
10. 临时路人、一次性地点、无持续价值物品不要轻易进入主要元素集；必要时写入事件详情。事件 `发生地点` 优先填写已注册父级地点或正式地点；`门口`、`女寝`、`客房` 等细粒度子空间只有持续复用、可独立检索或有稳定叙事功能时才注册为地点并设置父级地点。
11. 事件粒度要统一：事件应代表有叙事功能的剧情推进，不要把每句动作拆成事件。
12. 伏笔/线索必须有后续价值或明显悬念，不要把普通描述泛化成线索。
13. 所有交叉引用必须指向当前结构已有元素或本Delta新增元素。
14. **质量优先**：
    - **标签密度**：多使用有信息密度的标签。
    - **命名辨识度**：命名要有辨识度，不要把“那个男人”、“老者”等普通称呼当做主名称。
    - **详情价值**：充分记录非标准但有文学价值的信息。
    - **事件介绍**：每个事件介绍必须明确描述参与成员分别做了什么。
    - **不凑数量**：数量仅作为丰富度参考，绝不作为拆书提取的硬门槛。如果原文信息不足，绝对不得为了达标编造或新增无用元素。
15. 受控标签必须与 `references/narrative_taxonomy.json` 完全一致；角色只使用 `人物类型:*`；事件可使用剧情母题、叙事功能、冲突对象/议题、悬念问题/风险/机制、剧情线主题、爽点情绪点、冲突悬念类型、画面类型、视觉用途；其他事项只使用 `自由主题:*`。不带这些受控前缀的普通标签保持自由。
16. `叙事功能:*` 是普洛普 31 项的可选分析参照：不要求任何作品或章节覆盖 31 项，不要求按普洛普顺序出现，也不参与事件排序、最低数量或质量门槛。只在原文确有对应时标注。通俗的“开篇铺垫/冲突升级/转折/高潮”等功能可以写在复合分组第3段或普通标签中。
17. `剧情线主题:*`、`爽点情绪点:*`、`冲突悬念类型:*` 用于事件横向筛选；`画面类型:*`、`视觉用途:*` 用于筛出视觉资产候选。具体视觉描述不要塞进标签，写入详情或全书分析/视觉资产。
18. `自由主题:*` 收纳有价值的周边信息，包括但不限于世界规则、设定体系、叙事机制、主题母题、零散灵感、还没归类的设定、备用支线、彩蛋、创作备注等。不得把已经属于角色/事件/地点/线索/阵营/物品的事实放入其中。此标签不强制限制内容。
19. **标签自动压缩**：每章 Delta 生成后、合并到过程库后，`run_pipeline.py` 会自动调用 `scripts/compress_tags.py`，把所有带受控前缀（`剧情母题:`、`叙事功能:`、`人物类型:`、`画面类型:` 等出现在 `narrative_taxonomy.json` 顶层键中的前缀）的标签从 `标签集` 机械下层到 `详情.补充标签`，并按 `references/tag_limits.json`（事件 12、其余 8）对剩余自由标签 FIFO 截断、超额部分一并下层。这是确定性脚本步骤，不依赖 LLM。

## 顶层质量控制字段

Delta JSON 顶层的 `冲突声明` 和 `质量说明` 是 LLM 的"思维草稿区"：

- **`冲突声明`**（字符串数组）：原文信息前后矛盾、角色身份模糊、新增/修改归属不确定时，把疑虑写入此字段。这些声明不阻塞校验，保留在过程产物中供周期审计参考。
- **`质量说明`**（字符串）：对本章 Delta 整体质量的自我评估。例如本章信息增量少、大量新角色关系不明确暂按路人处理、某个线索可能是伏笔但证据不足等。

这两个字段**不参与合并**，不写入故事结构 JSON，仅保留在 Delta 文件中。它们的作用是让 LLM 有空间倾泻不确定信息，避免因"无处安放"而丢弃有价值的判断。

## 合并语义

`merge_delta.py` 对 `新增元素` 和 `修改元素` 采用字段级深度合并，**只增不删**：

| 字段类型 | 合并方式 |
|:---|:---|
| 元素匹配 | 按 `名称` -> `别名` 顺序查找；别名命中时合并到主元素 |
| `介绍` | 追加去重，不覆盖已有介绍 |
| 列表字段 | 去重合并，保持原顺序在前 |
| `详情` | 键级递归合并；`提取理由` 在 Delta 中保留用于审计，最终结构仅事件保留，非事件合并时丢弃；累计来源和旧版首次/最近章节不进入最终元素 |
| 标量字段 | Delta非空覆盖，空值/缺省跳过 |
| 顶层 `介绍` | 标题非空覆盖，描述追加去重 |

`详情` 中的非引用档案分两类处理。连续动作流水账只使用明确白名单字段并以 JSON 字符串数组追加去重，例如 `人物轨迹`、`地点轨迹`、`线索轨迹`、`阵营轨迹`、`物品轨迹`、`事项轨迹`，以及治理安全阀字段 `关系线索`、`待确认信息`、`冲突声明` 等。状态、属性、态度、秘密等快照可按原文自然生成少量稳定短键，如 `外貌细节`、`口癖台词`、`服饰线索`、`经营状态`、`空间氛围`、`当前修为`，值使用普通字符串；单章 Delta 入库时合并脚本会为这些非事件自由快照 Key 自动补 `0001-` 形式的章节前缀。事件集豁免前缀，事件详情的 JSON 字符串数组条目也不再写章节前导。`提取理由` 仍是 Delta 审计字段；若需要在最终结构中保留“为什么入库”，写入 `详情.入库依据`。

普通档案 key 不因包含标点、空格或下划线直接判错；这类问题只产生质量 warning。机器字段和明确引用字段仍严格规范，例如 `首次章节`、`最近章节`、`涉及章节`、`补充标签`、`关联线索`、`关联角色`、`关联事件`、`关联地点`。

## 入库前校验

每章 Delta 生成后，必须先运行：

```bash
python scripts/validate_delta.py <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

如果返回非0：
- 不允许 merge。
- 不重跑章节分析器。
- 只重跑 Delta提取器。
- 将校验报告保存到 `质量治理/delta校验/第{seq:03d}章_{title}.json`。

严格模式可用于质量优先场景：

```bash
python scripts/validate_delta.py --strict <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

## 合并后全量过程库校验

合并前先备份：

```bash
cp <项目目录>/故事结构_增量.json <项目目录>/故事结构版本/story_before_ch{seq:03d}.json
```

合并：

```bash
python scripts/merge_delta.py <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

合并后立即检查整个过程库：

```bash
python scripts/validate_structure.py --chapter-check <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

`--chapter-check` 的名字保留兼容旧命令，但实际语义是：每个切片合并后，对合并后的 `故事结构_增量.json` 执行全量 `process` 检查，并在报告开头列出本切片 Delta 触碰元素数量。它不是“只检查本章触碰元素”的局部校验。

如果失败：
```bash
cp <项目目录>/故事结构版本/story_before_ch{seq:03d}.json <项目目录>/故事结构_增量.json
```
然后只重跑 Delta提取器。

如果通过：
```bash
cp <项目目录>/故事结构_增量.json <项目目录>/故事结构版本/story_after_ch{seq:03d}.json
python scripts/progress_manager.py update <项目目录> 2 '{"已完成章节": [...], "总章节数": N}'
```

## 增量JSON膨胀应对

| JSON大小 | 输入策略 |
|:---|:---|
| < 80KB | 完整传给 Delta提取器 |
| 80-200KB | 传元素名称摘要 + 最近10章Delta，必要时按需读取完整JSON |
| > 200KB | 传主角/主要阵营/最近10章摘要，按需读取局部详情 |

即使只传摘要，Delta提取器也必须遵守：**修改元素只输出本章新揭示的信息，不凭摘要重写旧定义**。
