# 故事结构 JSON 硬规范

本规范定义 `故事结构_增量.json` 与最终 `故事结构.json` 的唯一合法结构。

> 重要：本 skill 是“拆书”，不是凭空创作。下面示例字段只说明结构，不得把示例名、示例关系、示例阵营写入实际结果。所有元素必须来自原文、章节分析或质量治理证据；不得为了满足数量要求编造原文不存在的元素。

## 1. 顶层结构

顶层允许以下 8 个字段；其中 `其他事项集` 为可选字段，缺失时按空数组处理，兼容既有项目。

```json
{
  "介绍": {
    "标题": "",
    "描述": ""
  },
  "角色集": [],
  "事件集": [],
  "地点集": [],
  "线索集": [],
  "阵营集": [],
  "物品集": [],
  "其他事项集": []
}
```

### 介绍

```json
{
  "标题": "",
  "描述": ""
}
```

- `标题`：故事名称。
- `描述`：故事简介，通常包含故事背景、设定、剧情纲要，可以写长一点。
- `介绍` 对象只能包含 `标题`、`描述` 两个字段。

## 2. 公共字段

以下字段存在于所有基础元素中：

```json
{
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {}
}
```

规则：

- `别名`：string[]。
- `标签集`：string[]。普通无前缀标签可自由使用；受控叙事标签遵照第 10 节。可为空：仅保留有检索、筛选、聚合或导航价值的标签。
- `介绍`：string，尽可能详细说明该元素在故事中的作用和意义。
- `详情`：object，用于放置非标准字段。
- 除标准字段和公共字段外，不允许在元素顶层新增字段；非标准信息必须放入 `详情`。

## 3. 角色

```json
{
  "名称": "",
  "是否主角": false,
  "性别": 2,
  "年龄": 0,
  "生日": "0001-01-01T00:00:00",
  "所属阵营": [],
  "关系": [],
  "分组": "",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {
    "首次章节": "0001",
    "最近章节": "0001"
  }
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `是否主角`：boolean。
- `性别`：integer，只能为 `0/1/2`，其中 `0=男`、`1=女`、`2=未知`。
- `年龄`：integer。原文未知时填 `0`，不得编造默认年龄。
- `生日`：ISO 时间。原文未知固定填 `0001-01-01T00:00:00`；该值表示未知，不参与真实出生时间排序。
- `详情.首次章节`、`详情.最近章节`：固定宽度章节序号字符串，例如 `0001`、`0050`。
- `所属阵营`：string[]，每一项必须是 `阵营集` 中已存在的正式名称。
- `关系`：string[]，格式必须是 `关系类型:角色正式名称`，目标角色必须存在。
- `分组`：string，可用 `/` 表示层级；若上层之下仅有一个下层，不必分层。

## 4. 事件

每个事件代表故事中的剧情单元。

```json
{
  "名称": "",
  "发生地点": "",
  "参与成员": [],
  "重量级": 0,
  "目标事件": [],
  "分组": "00000010-退婚尊严线冲突爆发羞辱反击身份尊严",
  "时间": "0001-01-01T00:00:00",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {
    "涉及章节": "0001"
  }
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `发生地点`：string，优先使用 `地点集` 中已存在的正式名称或父级地点。过程/治理阶段允许未注册细粒度子空间作为 warning 保留；最终交付前应收敛为已注册正式地点。`门口`、`女寝`、`客房` 等没有持续叙事价值的子空间写入事件 `详情.具体地点`、`详情.场景位置` 或 `介绍`，不要机械注册为地点。
- `参与成员`：string[]，每一项必须是 `角色集` 中已存在的正式名称。
- `重量级`：integer，取值 `0-100`。
- `目标事件`：string[]，每一项必须是 `事件集` 中已存在的正式名称，表示由本事件导致、铺垫或发展到的后续事件。
- `时间`：章节时间。第001章为 `0001-01-01T00:00:00`，每个后续章节序号加一天；必须等于最小 `详情.涉及章节` 对应的时间，不表示原著日历。
- `详情.涉及章节`：string，固定宽度、升序、去重，以中文逗号连接，例如 `0043，0044，0045`。
- `分组`：string，格式为 `8位段号-40字以内复合剧情段短名`，例如 `00000010-退婚尊严线冲突爆发羞辱反击身份尊严`。段号用于页面排序而非章节定位；同一完整分组只允许覆盖同一章节内的一个连续事件区间，原始事件数组仍按章节逻辑顺序排列。
- `分组` 短名必须压缩包含剧情、剧情线主题、叙事功能、爽点/情绪点、冲突悬念类型，不能只写普通剧情名、主题、标签、章节号或纯编号；不得使用 `+` 分隔长格式，治理脚本会按事件数组顺序重排8位段号。
- 跨剧情段可复用的主题、功能、爽点、冲突悬念、视觉信息仍可写入 `标签集`；跨章节主线在后续全书分析中汇总，不作为逐章事件分组的硬约束。`分组` 是事件目录中同一章节内连续剧情段的排序和高密度浏览摘要。
- 每个事件的 `标签集` 必须保留一个四维复合标签，格式为 `剧情线主题+叙事功能+爽点/情绪点+冲突悬念类型`，例如 `侠之真义+主题点化+感动+观念冲突`。该标签不包含段号和剧情段名，因为这些由 `分组` 承担；该标签不带冒号，必须留在 `标签集` 供界面直读，不下沉到 `详情.补充标签`。
- `详情.剧情段`：可选自由字符串，推荐用 `-` 描述人物、势力、地点、冲突、目标、叙事功能、爽点情绪点、冲突悬念，不参与页面排序或聚合。
- `详情.关联线索`：可选 `线索:名称` 字符串数组，用于跨剧情段关联已有线索。
- `详情.视觉等级`、`详情.画面类型`、`详情.核心画面`、`详情.镜头建议`、`详情.氛围`、`详情.视觉理由`、`详情.视觉用途`：可选字符串字段，用于视觉资产/分镜/AI绘图生产资料；不要为了视觉完整性编造原文不存在的画面。
- `介绍`：必须详细描述事件起因、发展过程和后续影响；如果有参与成员，必须描述他们在事件中做了什么。

## 5. 地点

地点是故事中物理存在的位置。

```json
{
  "名称": "",
  "父级地点": "",
  "分组": "",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {
    "首次章节": "0001",
    "最近章节": "0001"
  }
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `父级地点`：string，若非空，必须是 `地点集` 中已存在的正式名称，且不能指向自身。
- `分组`：string，可用 `/` 表示层级。
- `介绍`：需有环境描述和其在故事中的重要性。
- 子空间注册原则：只有持续复用、可独立检索或具备稳定叙事功能的子空间才进入 `地点集`，并用 `父级地点` 挂到上级地点；一次性方位描述应留在事件详情。

## 6. 线索

每个线索代表一条故事线。

```json
{
  "名称": "",
  "涉及事件": [],
  "分组": "",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {
    "首次章节": "0001",
    "最近章节": "0001"
  }
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `涉及事件`：string[]，每一项必须是 `事件集` 中已存在的正式名称。
- `分组`：string，可用 `/` 表示层级。
- `介绍`：需说明线索如何贯穿多个事件、推动故事发展。

## 7. 阵营

每个阵营代表故事中的国家、帮派、组织或势力。

```json
{
  "名称": "",
  "父级阵营": "",
  "座落地点": "",
  "分组": "",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {
    "首次章节": "0001",
    "最近章节": "0001"
  }
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `父级阵营`：string，若非空，必须是 `阵营集` 中已存在的正式名称，且不能指向自身。
- `座落地点`：string，若非空，必须是 `地点集` 中已存在的正式名称。
- `分组`：string，可用 `/` 表示层级。
- `介绍`：需说明目标、内部结构和与其他阵营的关系。

## 8. 物品

物品可以是武器、装备、信物或任意剧情需要的物品。

```json
{
  "名称": "",
  "分组": "",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {
    "首次章节": "0001",
    "最近章节": "0001"
  }
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `分组`：string，可用 `/` 表示层级。
- `介绍`：需说明独特用途和背景故事。

## 9. 其他事项集

每个其他事项代表原文中具有跨事件价值、但不属于角色/事件/地点/线索/阵营/物品的非实体知识。它不收纳拆书者的个人读后感、外部作者背景、实操规划或无原文证据的推测。

```json
{
  "名称": "",
  "分组": "",
  "别名": [],
  "标签集": [],
  "介绍": "",
  "详情": {}
}
```

字段规则：

- `名称`：string，非空，同类型内唯一。
- `分组`：string，可用 `/` 表示层级。
- `介绍`：string，对该自由主题内容的说明。
- `详情`：object，用于放置非标准字段，遵照公共规则。
- 本字段为可选项，不要求必须填充，也不设置最低数量要求。

## 10. 叙事分类词库

`references/narrative_taxonomy.json` 是受控叙事标签的唯一来源。标签带有下列前缀时，必须使用该文件中存在的值，且只能放在对应集合：

| 集合 | 允许的受控前缀 |
|---|---|
| `角色集` | `人物类型:` |
| `事件集` | `剧情母题:`、`叙事功能:`、`冲突对象:`、`冲突议题:`、`悬念问题:`、`悬念风险:`、`悬念机制:`、`剧情线主题:`、`爽点情绪点:`、`冲突悬念类型:`、`画面类型:`、`视觉用途:` |
| `其他事项集` | `自由主题:` |

规则：

1. 受控前缀出现在错误集合中，或其值不在词库中，均为校验错误。
2. 没有上述受控前缀的普通标签保持自由，兼容既有项目。
3. `剧情母题:` 使用 Polti 的 36 种戏剧处境，表达故事的高层处境；它不取代事件的事实介绍。
4. `叙事功能:` 使用普洛普 31 项功能，仅作为可选分析参照。任何作品或章节可以一个也不使用；不要求覆盖 31 项，不检查标签先后顺序，也不参与事件排序、最低数量或质量门槛。
5. 冲突词库固定为 14 项：7 个 `冲突对象:` 与 7 个 `冲突议题:`；悬念词库固定为 12 项：8 个 `悬念问题:`、3 个 `悬念风险:` 与 1 个 `悬念机制:`。
6. `剧情线主题:`、`爽点情绪点:`、`冲突悬念类型:` 用于事件横向筛选；它们可以与事件 `分组` 的40字以内复合短名互相呼应，但不取代连续剧情段分组。
7. `画面类型:`、`视觉用途:` 只标记视觉资产入口；具体画面、镜头、氛围和可视化理由写入事件 `详情`，并在全书分析阶段汇总为视觉资产表。
8. `自由主题:` 包括但不限于世界规则、设定体系、叙事机制、主题母题、零散灵感、还没归类的设定、备用支线、彩蛋、创作备注等（不强制限制）。主题母题必须有跨章节的明确文本证据；世界运行机制归入世界规则而非叙事机制。
9. 事件四维复合标签使用无冒号自由标签格式：`剧情线主题+叙事功能+爽点/情绪点+冲突悬念类型`。它是界面直读标签，不属于受控前缀标签，不应被治理或压缩下沉。
10. `题材类型` 词库保留供全书分析阶段判定题材使用，不作为逐章事件受控标签；逐章事件不使用 `题材类型:` 前缀。

## 11. 详情字段硬规则


`详情` 不保存累计的 `来源章节`、`首次出现章节`、`最近更新章节`。`提取理由` 在 Delta JSON 中必须存在，用于审计本章为什么提取或更新该元素；最终故事结构只允许事件保留 `详情.提取理由`，其他元素使用上述紧凑章节字段和自身详情追溯，不保存该 Delta 理由。若“为什么入库/为什么更新”本身有长期档案价值，写入 `详情.入库依据`。

`详情` 用来放置非标准字段，但必须满足以下规则：


1. `详情` 必须是 object。
2. `详情.补充标签` 是标签治理专用字段：值必须为可解析、非空、去重的 JSON 字符串数组，例如 `"[\"热血\",\"初入江湖\"]"`；其中的标签不得与顶层 `标签集` 重复。
3. `详情.关系线索`、`详情.待确认信息`、`详情.疑似信息`、`详情.冲突声明`、`详情.待确认关系`、`详情.待确认引用` 是长期累计字段，推荐使用可解析、去重的 JSON 字符串数组；它们用于沉淀暂不结构化的信息，不表示后续必须自动回补。
4. 档案型长期累计字段只按明确白名单处理，值使用可解析、去重的 JSON 字符串数组，合并时追加而非覆盖。角色/地点/线索/阵营/物品/其他事项的连续动作流水账使用 `人物轨迹`、`地点轨迹`、`线索轨迹`、`阵营轨迹`、`物品轨迹`、`事项轨迹` 等专用字段；治理安全阀字段如 `关系线索`、`待确认信息`、`冲突声明` 也保持累计数组语义。
5. 状态、属性、态度、秘密等自然生成的非引用快照字段使用普通字符串。单章 Delta 入库时，非事件集合的自由快照 Key 会由合并脚本自动补 `0001-` 形式的章节前缀；机器字段、`补充标签`、`关联线索`、`关联角色`、`关联事件`、`关联地点` 等结构引用字段不加前缀。事件集本身由 `详情.涉及章节` 表达时序，事件详情 Key 不加章节前缀，事件详情中的 JSON 字符串数组条目也不写章节前导。
6. 机器字段和明确引用字段的键名必须严格稳定，不可包含标点符号、空格或下划线，例如 `首次章节`、`最近章节`、`涉及章节`、`补充标签`、`关联线索`、`关联角色`、`关联事件`、`关联地点`。普通档案字段优先使用中文、英文或数字短键，但允许为保真包含少量标点；key 太长、像整句台词、含大量标点时只 warning，不阻塞合并。完整台词、动作、冲突和证据应放在 value 中。
7. 值只能是 string 或 string[]。
8. 禁止 number、boolean、null、object 等值类型。
9. string 值不做短文本限制，应尽量完整承载对应元素的档案信息；不要因为 key 严格而压缩或省略 value 中的动作、冲突、信息、情绪、台词和状态变化。
10. 如果 string 指代故事元素，必须严格使用 `类型:名称` 格式。
11. 允许类型只有：`角色`、`事件`、`地点`、`线索`、`阵营`、`物品`。
12. 指代故事元素时，`名称` 必须是对应元素集中的正式名称，不建议使用别名。
13. 真实 JSON Array 仅用于指代多个故事元素；数组中每一项都必须是 `类型:名称` 格式，例如 `"关联线索": ["线索:资金缺口"]`。
14. 非引用型多值档案内容不要写真实 JSON Array；多段动作、台词、情绪递进等如需保持数组语义，请写成 JSON 字符串数组，例如 `"动作链条": "[\"赖床\",\"装病\",\"咳血\",\"被送医威胁\"]"`。标签降级的多值列表只能写入 `详情.补充标签`，其值是可解析的 JSON 字符串数组，例如 `"[\"人物类型:核心主角\"]"`。

## 12. 数量要求

数量仅作为丰富度参考，不作为拆书提取硬门槛。
如果原文不足，不得为达标新增元素。

## 13. 硬校验脚本

最终交付前必须运行：

```bash
python scripts/validate_structure.py --strict <项目目录>/故事结构.json
```

该命令会校验：

- 顶层字段是否精确。
- 每类元素字段是否精确。
- 是否存在规范外字段。
- 所有标准字段类型和值域是否正确。
- `详情` 键和值是否合规。
- 所有交叉引用是否指向已存在的正式名称。
- 是否存在重复名称、别名冲突、父级循环。
- 最低数量、介绍、分组、标签等最终交付质量项。
