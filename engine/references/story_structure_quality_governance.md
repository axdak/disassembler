# 故事结构质量治理说明

## 目标

本 Skill 的故事结构维护采用“过程数据库 + 最终交付文件”双层设计：

- `故事结构_增量.json`：过程数据库，服务于逐章上下文、断点续跑、信息积累。
- `故事结构.json`：最终交付文件，服务于高质量结构化分析、后续创作、改编和检索。

逐章阶段不追求每一轮 `故事结构_增量.json` 文学整理质量完美，但必须保证它结构合法、引用自洽、来源可追踪、错误可回滚。

## 为什么不采用每章全量重写

每章让模型读取上一版完整JSON并返回新版完整JSON，会带来以下风险：

1. JSON越到后面越大，输入和输出都膨胀。
2. 模型可能遗漏旧角色、旧事件、旧伏笔。
3. 模型可能静默改写前面已经确定的信息。
4. 某一章输出质量差，会污染整个全局结构。
5. 断点恢复时很难判断是哪一章改坏的。

因此，本 Skill 只允许模型在逐章阶段输出 `Delta/Patch`，不允许每章输出完整新故事结构。

## 四层治理

### 第一层：章节分析与Delta提取分离

章节分析器只输出 MD：

```text
当前章节原文 -> 第N章_章节分析.md
```

Delta提取器再读取：

```text
当前故事结构_增量.json + 当前章节原文 + 第N章_章节分析.md
```

只输出：

```text
第N章_delta.json
```

这样可以让文学理解和严格结构化分开，提高JSON稳定性。

### 第二层：Delta入库前校验

合并前必须运行：

```bash
python validate_delta.py <故事结构_增量.json> <第N章_delta.json>
```

检查：

1. JSON格式是否合法。
2. 顶层字段是否符合规范。
3. 新增元素是否有完整标准字段。
4. 修改元素是否只包含合法增量字段。
5. 字段类型和值域是否正确。
6. 是否存在未知字段。
7. 是否存在空名称。
8. Delta内部是否存在重复名称。
9. 是否引用不存在的人物、地点、阵营、事件、线索、物品。
10. 新增元素是否其实已存在于当前结构。
11. 每个新增/修改元素是否在 `详情` 中提供非空 `提取理由`；它是 Delta 审计字段，说明该元素为什么值得提取或本章为什么更新它。最终故事结构只允许事件保留 `详情.提取理由`，非事件不得沉淀该字段；若该理由有长期档案价值，应另写入累计字段 `详情.入库依据`。
12. 角色生日是否为合法 ISO 时间；事件时间是否等于最小涉及章节对应的章节时间。
13. 事件涉及章节是否为固定宽度、升序、去重字符串，事件数组是否按最小涉及章节非递减，分组段号是否按连续剧情段顺序递增；事件分组是否采用 `8位段号-40字以内复合剧情段短名`，且短名压缩包含剧情、剧情线主题、叙事功能、爽点/情绪点、冲突悬念类型；同名短名跨章节时是否已经切为新的段号。

不通过则不得合并，只重跑Delta提取器。

### 第三层：合并后全量过程库校验

合并后必须运行：

```bash
python validate_structure.py --chapter-check <故事结构_增量.json> <第N章_delta.json>
```

该模式保留 `--chapter-check` 名称用于兼容既有命令，但实际语义是：对合并后的整个 `故事结构_增量.json` 执行 `process` 级全量检查，并在报告中附带本章 Delta 触碰元素数量。它不是最终强校验，也不是只检查本章触碰元素的局部校验。

三档检查分工：

```text
每章提交后：全量 process 检查
  保证过程库整体可读、字段/类型/骨架合法，可继续下一切片。

周期/按需治理后：全量 governance 检查
  引用错误升级为 error，用于发现治理补丁、合并、重命名、降级带来的全局问题。例外：事件 `发生地点` 指向未注册细粒度子空间时，governance 保留为 warning；最终交付前再收敛为已注册父级地点或正式地点。
  同时检查顶层 `介绍`：标题有原文依据时补齐；已有足够主线、主角和核心冲突材料而描述为空时，补阶段性故事简介。已有描述仅在明显失真时更新，不逐轮追加过程笔记。

最终交付前：全量 final/strict 检查
  强 Schema、引用、最低数量、介绍完整性等核心质量项必须全部通过。
```

检查重点：

- 本章事件的参与成员是否存在。
- 本章事件的发生地点是否存在；未注册细粒度子空间不阻断 governance，但应判断是否需要注册为正式地点，或改用父级地点并把具体位置写入事件详情。
- 本章线索涉及事件是否存在。
- 本章角色所属阵营和关系引用是否存在。
- 角色 `关系` 字段只能引用已存在的正式角色；治理时遇到未入库目标，不得直接删除有原文依据的关系线索。若目标角色已明确出场且具备持续价值，可在本次治理中显式新增/合并为正式角色；否则将该关系从 `关系` 数组移入 `详情.关系线索`，保留为长期档案线索。`详情.关系线索` 使用 JSON 字符串数组，例如 `"[\"父亲:郭巨侠；来源:第003章；目标角色未正式入库\"]"`。注意 `详情` 中的 `角色:名称` 会继续按结构引用校验，未入库目标不得写成显式引用。
- 审计时若发现人物、地点、线索、阵营、物品只剩机器字段，应补充可读档案。连续动作流水账使用 `人物轨迹`、`地点轨迹`、`线索轨迹`、`阵营轨迹`、`物品轨迹` 等专用字段，值必须是 JSON 字符串数组，治理追加时会去重累加；状态、属性、态度、秘密等快照使用稳定短键和普通字符串，不依赖后缀泛匹配累计。
- 本章阵营父级和座落地点是否存在。
- 本章地点父级是否存在。
- 本章详情字段中的 `类型:名称` 引用是否存在。

失败时回滚到合并前快照，只重跑Delta提取器。

### 第四层：周期审计与最终整理

每5-10章触发一次结构审计，审计器读取：

```text
当前故事结构_增量.json
最近5-10章完整原文
最近5-10章章节分析MD
最近5-10章Delta JSON
上一周期 correction（如有）
```

审计目标：

1. 合并重复角色/地点/阵营/物品。
2. 识别别名被当成新元素的问题。
3. 降级临时路人和无持续价值元素。
4. 调整事件粒度。
5. 整理伏笔和线索。
6. 补充缺失关系。
7. 标记需要进一步复核的冲突，并将其作为下一次自动修复的输入。
8. 对治理新增的历史聚合事件按最小涉及章节插入；对既有事件只允许重分类，不允许改变时间、涉及章节或数组位置。
9. 治理后按事件数组顺序全量重排8位剧情段号；章节边界必须切为新段号，即使短名相同。分组名优先保留/补足40字以内复合剧情段短名，短名需压缩包含剧情、剧情线主题、叙事功能、爽点/情绪点、冲突悬念类型；跨章节主线、线索关联和视觉信息在后续全书分析中汇总，不用于逐章事件分组。
10. 标签治理只保留支持跨元素检索、筛选、聚合或导航的标签。每项 `治理操作.治理标签` 必须给出保留标签、降级标签和理由，二者完整覆盖原标签集；降级标签以可逆 JSON 字符串数组写入 `详情.补充标签`，不允许静默丢弃。
11. 关系引用治理采用“显式结构化或下沉沉淀”原则：不能为了通过校验把 `父亲:某人`、`哥哥:某人` 这类有依据但目标未入库的关系直接抹掉；只有确认是误识别或无依据时才删除。暂不能结构化的关系应保留在角色 `详情.关系线索` 中，作为长期档案信息，不设置自动回补要求；若后续确需提升为标准 `关系`，必须通过明确治理补丁显式新增/合并目标角色并追加关系。
12. 档案信息治理采用“轨迹累计、快照分章”原则：跨章节连续动作使用 JSON 字符串数组字段，例如 `人物轨迹`、`地点轨迹`、`物品轨迹`、`阵营轨迹`、`线索轨迹`；状态、属性、态度、秘密等快照使用普通字符串自由短键，单章入库时由合并脚本自动补章节前缀，避免同名覆盖。

审计器输出 `correction_delta.json`，不得直接覆盖完整JSON。

持续拆书时，周期审计由主控Agent接力完成。`run_pipeline.py run` 在每个周期点执行：

```text
生成/更新 audit_001-005.md
↓
返回 `2`，交接给主控Agent读取任务包并生成真实 correction_001-005.json
↓
再次运行 run 后，validate_delta --mode governance → merge_delta → apply_governance_ops → validate_structure --mode governance
↓
失败则读取校验报告并重写补丁，再次运行 run
↓
通过后才进入下一章
```

返回 `2` 是正常的待办交接，不是失败。主控Agent必须自行完成审计并写出真实补丁；禁止空 Delta、伪造 worker 或跳过审计。补丁校验失败时，主控Agent读取生成的校验报告并修复补丁，直到通过或遇到源文件、权限、必要工具等硬阻塞。

审计包默认保持单周期、单任务包、单补丁。默认以 160000 字符作为面向 256k 上下文模型的保守输入预算，可用 `run --audit-max-context-chars` 或 `audit-pack --max-context-chars` 覆盖。构建器先尝试完整历史结构；接近预算时只将历史结构降为索引或“索引 + 本周期关联元素详情”，本周期原文、章节分析和 Delta 不得静默截断。若多章周期仍超预算，管线自动把父区间二分为连续子区间，父状态为 `split_pending`，子区间各自产生真实审计任务包和 correction；全部子区间提交后父状态变为 `covered_by_children`，恢复时只重放子区间 correction。只有单章证据仍超预算时才保留 `blocked_context` 并返回失败；此时调整预算或模型后再重新生成。

周期补丁可以用顶层 `章节范围` 表示审计范围；该字段只在 `validate_delta.py --mode governance` 中有效。逐章 Delta 仍必须使用单章 `章节` 字段。

若周期内确实无需治理，必须显式声明 no_change：补丁顶层带 `治理类型: "no_change"` + 非空 `质量说明` + 非空 `证据范围`（已审计章节数组）；`新增元素 / 修改元素 / 治理操作` 全空但缺这三项元数据的补丁会被 `validate_delta.py --mode governance` 直接拦截。详见 `governance.md`。

最终阶段允许模型生成完整 `故事结构_草稿.json`，但必须经过：

```bash
python validate_structure.py --strict <故事结构_草稿.json>
```

通过后才能写入 `故事结构.json`。

## 回滚策略

每章合并前保存：

```text
故事结构版本/story_before_chNNN.json
```

每章合并通过后保存：

```text
故事结构版本/story_after_chNNN.json
```

若某章校验失败：

1. 用 `story_before_chNNN.json` 覆盖 `故事结构_增量.json`。
2. 保留失败的Delta和校验报告。
3. 重跑Delta提取器。
4. 再执行入库前校验、合并、章节级校验。

若后面才发现某章污染结构：

1. 找到最近可信快照。
2. 从该快照后一章开始重放Delta。
3. 对可疑章节强制重跑Delta提取器。

## 过程JSON与最终JSON的边界

`故事结构_增量.json` 允许：

- 某些角色简介还不够精炼。
- 某些事件粒度需要最终统一。
- 某些伏笔需要后续判断是否有效。
- 某些人物关系处于待确认状态。

但不允许：

- JSON格式错误。
- schema不合法。
- 关键字段缺失。
- 本章新增/修改元素交叉引用错误。
- 无依据覆盖旧事实。
- 无法追踪来源章节。

`故事结构.json` 必须：

- 去重完成。
- 引用自洽。
- 分组统一。
- 事件顺序合理。
- 伏笔/线索质量高。
- 人物关系清晰。
- 符合 `story_structure_spec.md`。
