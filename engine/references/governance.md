# 周期结构审计与质量治理规则

## 周期审计触发

默认每5章触发一次；如果小说较长，可以每10章触发一次。若存在明显卷/篇/大剧情节点，应优先按剧情阶段触发。

推荐规则：

```text
20章以内：中段审计1次 + 最终审计
20-50章：每5章审计1次
50章以上：每10章审计1次，或按卷审计
```

## 审计输入
- 当前 故事结构_增量.json
- 本周期最近5-10章的完整原文
- 本周期最近5-10章分析MD
- 本周期最近5-10章Delta JSON
- 上一个周期的 correction（如有）

审计包始终是一个周期、一份任务包和一份 correction。构建器优先保留本周期原文、分析和 Delta；只有总包接近模型上下文预算时，才把历史结构从完整 JSON 降载为全局索引或“索引 + 本周期关联元素详情”。

`audit-pack --max-context-chars` 和 `run --audit-max-context-chars` 可配置单包字符预算；默认 160000 字符，面向 256k 上下文模型预留补丁输出、系统提示和工具调用。它是模型无关的保守字符预算，不宣称等同于任意供应商的精确 Token 计数。

若连历史结构降载后的单包仍超预算，不得截断本周期原文、分析或 Delta，也不得用空补丁解除阻断。多章周期会自动二分为连续子区间，并在父状态文件写入 `split_pending` 与 `child_ranges`；子区间全部通过真实 `correction_XXX.json` 提交后，父区间自动标记为 `covered_by_children`。只有单章证据仍超预算时，状态才保持 `blocked_context` 并返回失败；此时应提高预算或改用更大上下文模型后重新生成。

## 审计目标
检查并修正：
1. 重复角色合并/别名修正。
2. 临时路人降级清理。
3. 事件粒度重整。
4. 伏笔/线索归集、价值过滤。
5. 地点、阵营垃圾元素清理。
6. 不确定信息的澄清。
7. （必要时）补充缺失的关键事实。

## 审计输出
不要直接重写完整故事JSON，只输出 `correction_delta.json`（补丁格式，参见 `prompts/audit.j2` 及 `schemas/audit_correction.schema.json`）。

其中 `新增元素` 和 `修改元素` 部分仍走：

```bash
python scripts/validate_delta.py <故事结构_增量.json> correction_delta.json
python scripts/merge_delta.py <故事结构_增量.json> correction_delta.json
python scripts/validate_structure.py --chapter-check <故事结构_增量.json> correction_delta.json
```

审计报告保存到 `质量治理/周期审计/`。

## 无需治理时的合法表达：no_change 补丁

周期审计在结构干净时仍**必须真实完成**，但允许显式声明"无修改"。规则：

- 当 `新增元素`、`修改元素`、`治理操作` 全部为空时，`validate_delta.py --mode governance` 会强制要求以下顶层字段：
  - `治理类型`: 固定值 `"no_change"`
  - `质量说明`: 非空字符串，写明已检查的维度与无需修改的理由
  - `证据范围`: 非空字符串数组，列出本周期已审计章节（如 `["第001章", "第002章", ...]`）
- 任何其中一项缺失或为空，校验器直接报错；这是为了把"真实审计后认为无需修改"与"为跳过审计写空补丁"区分开。
- 一旦补丁包含任何新增、修改或治理操作，上述三字段恢复为可选。

示例：

```json
{
  "章节范围": "第001章-第005章",
  "治理类型": "no_change",
  "质量说明": "已检查角色、事件、地点、线索、阵营、物品，无重复或降级需求。",
  "证据范围": ["第001章", "第002章", "第003章", "第004章", "第005章"],
  "新增元素": {"角色集": [], "事件集": [], "地点集": [], "线索集": [], "阵营集": [], "物品集": []},
  "修改元素": {"角色集": [], "事件集": [], "地点集": [], "线索集": [], "阵营集": [], "物品集": []}
}
```

## 三档校验与规范化治理
治理期间不得粗暴删除 `故事结构_增量.json` 中因为版本遗留的历史字段，而应使用保全式脚本：
`python scripts/normalize_story_schema.py <项目目录>/故事结构_增量.json --in-place --backup`

校验档位：
- `--mode process`: 每章日常提交。
- `--mode governance`: 周期治理后，强校验引用，规范标签；事件 `发生地点` 的未注册细粒度子空间仅作为 warning，避免治理被临时方位词卡住。
- `--mode final`: 最终交付前的最严格卡口。

## 故事结构质量保障原则
1. **不追求每章后增量JSON文学质量完美**，但每章后必须结构合法、引用自洽、可追踪、可回滚。
2. **不允许模型每章全量重写故事结构JSON**。
3. **所有模型修正都应优先输出Delta/Patch**。
4. **合并前必须校验Delta**，合并后必须做全量过程库校验。
5. **周期审计只输出 correction_delta.json**，不得直接覆盖完整结构。
6. **最终结构整理阶段可以生成完整草稿JSON**，但必须经过 `validate_structure.py --strict`。
7. **发现坏章时回滚到上一章快照，只重跑Delta提取器**。
8. **断点恢复时以文件系统、进度JSON、故事结构快照三者共同判断状态**。

## 元素质量要求
1. 剧情符合逻辑。
2. 交叉引用自洽。
3. 标签丰富、有信息密度。
4. 分组统筹安排：事件分组采用 `8位段号-40字以内复合剧情段短名`，短名需压缩包含剧情、剧情线主题、叙事功能、爽点/情绪点、冲突悬念类型。
5. 事件分组不分层，按行文顺序排列。
6. 命名有辨识度，不把普通称呼当主名称。
7. 介绍详尽，事件必须描述参与成员行为。
8. 详情字段充分记录非标准但有价值的信息。
9. 未确认信息不得写成确定事实。
10. 数量仅作为丰富度参考，不作为拆书提取硬门槛。如果原文不足，不得为达标新增元素。
11. 主动/周期治理应检查顶层 `介绍`：标题有原文依据时补齐；积累到足以识别主线、主角和核心冲突时补阶段性故事简介。已有描述仅在明显失真时更新，不把每轮审计结论追加进描述；最终整理阶段统一重写为正式全书简介。
